Security Toolkit

Python · cryptography (Fernet) · PBKDF2 · secrets · Streamlit

A set of connected security tools built on shared code: a password strength checker, a password generator, a login system, and file and text encryption.

What was hard

The hardest part for me when creating the security toolkit was understanding the various types of cryptogrophy techniques and which situation each one is used in. I had to also wrap my head around my Fernet needed b64encode for creating symmetric secret keys for encryption and decryption.

  • Hashing vs. encryption. Passwords need a one-way hash you can only verify, while files need encryption you can reverse with the right key. I used PBKDF2 for the login system and Fernet for encryption, and had to keep the two ideas straight.
  • Storing the salt with the data. Every encryption uses a fresh random salt, so decrypting means splitting the salt back off the front of the encrypted blob and re-deriving the same key from the password.
  • Generating passwords that are actually random. The generator guarantees at least one character from each selected type, then shuffles everything with a cryptographically secure shuffle so those required characters don't always sit at the start.

What I did

  • Strength checker that estimates entropy, scores length and character variety, flags repeats and sequences, and rejects anything on a 10,000-entry common-password list.
  • Login system that salts and hashes passwords with PBKDF2 (100,000 iterations) and returns the same generic error for a wrong username or a wrong password, so it doesn't reveal which accounts exist.
  • Encryption engine that derives a key from a password with PBKDF2 (480,000 iterations) and encrypts with Fernet, with wrong-password attempts caught and rejected cleanly.
  • Tested every module with round-trip checks: encrypt then decrypt, register then log in, and confirm wrong passwords fail.

Bank Security Transactional System

Python · Flask · bcrypt · JWT · flask-limiter · Bash · cron · Splunk

A small banking backend with a web front end ("VaultBank"), built to practice securing an application end to end and then proving the security works with automated tests and monitoring.

What was hard

  • Conversion from Python to Frontend.Embedding the logical functions of the python code into the frontend with JavaScript and HTML.
  • Password hashing. bcrypt works on bytes, not strings, and mixing the two caused login failures until I fixed the encoding on both the hashing and checking sides.
  • Token handling. Getting JWTs issued, sent, and validated correctly on every protected route, and rejecting bad or missing tokens.
  • A design flaw I fixed mid-project. Registering a user and creating a bank account were separate steps, which let the two drift apart. I refactored so registration creates the account and the username is the account ID.

What I did

  • Added rate limiting on login with flask-limiter, keyed by client IP, so repeated attempts get an HTTP 429 after 5 tries.
  • Wrote security_test.py, an audit script that tests unauthenticated access, rate limiting, and invalid-token rejection, and writes timestamped results to a log.
  • Wrote run_audit.sh to start Flask in the background, confirm it is up with curl, run the audit, and shut the server down, plus rotate_logs.sh for log rotation. Both run nightly on cron.
  • Fed the audit log into Splunk Enterprise and built a four-panel SIEM dashboard in SPL: warnings over time, rate-limit hits by status code, audit run timeline, and pass/fail counts.

NFL Analytics Dashboard

Python · Flask · pandas · nfl_data_py · Chart.js

A web dashboard that pulls real NFL game data and shows a team's season at a glance: points per game, win/loss record, home vs. away performance, and averages.

What was hard

The hardest part when designing the Analytics Dashboard was figuring out what information from the dataset was useful and how I was going to set it up in Pandas so that it stays generic so I can create a dashboard for every team.

The game data doesn't have a column for "my team's score." Each row has a home score and an away score, so which number belongs to the team depends on where they played. I used a row-wise apply in pandas to pick the right score for every game before calculating anything.

What I did

  • Built a Flask backend with JSON endpoints for scores and home/away splits, and a front end that renders bar and doughnut charts with Chart.js.
  • Started with only the 2024 Eagles, then generalized it: a 32-team picker and dynamic routes like /api/scores/<team>, with one get_team_data(team) function replacing the hardcoded version.
  • Each team got its own logo and when the logo was pressed by the user, all the programmed stats of the team from the 2024 was displayed.
